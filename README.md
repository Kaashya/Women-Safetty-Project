# Women Safety Analytics — CCTV Safety Monitoring Prototype

An AI-assisted video monitoring prototype that processes uploaded clips, detects and tracks generic people, and surfaces potential safety events for human review.

> **IMPORTANT DISCLAIMER**  
> Alerts generated by this system represent **potential safety events requiring human verification** and **NOT confirmed crimes, harassment, or definitive emergencies**. New events start as `pending` and require a human operator to verify or dismiss them before any operational action is taken.

## 4. How to Run

### A. Run the final Streamlit dashboard

From the repository root, activate the virtual environment and run:

```bash
streamlit run src/dashboard/app.py
```

In the sidebar, upload an MP4, AVI, MOV, or MKV clip, optionally set its camera ID, and select **Start Analysis**. The app displays the annotated feed as Member 1 processes each frame and Member 2 evaluates the same frame for potential events. **Stop / Reset** stops processing and clears the current video state; the SQLite event history is preserved.

The dashboard creates `data/events.db` automatically. Uploaded videos are written to a temporary file for OpenCV and removed when processing ends or is reset. Video inference runs as fast as the available hardware allows.

### B. Run Member 2 Integrated Safety Demo (`demo_safety.py`)

Run real-time detection, tracking, distress gesture detection, and sustained proximity analysis:

```bash
# Interactive visual playback with bounding boxes and safety alert banners:
python demo_safety.py --video data/v2.mp4

# Run in headless mode and save annotated output video:
python demo_safety.py --video data/v2.mp4 --headless --save

# Custom tuning (e.g. 1.0s distress hold, 2.0s proximity duration):
python demo_safety.py --video data/v2.mp4 --distress-hold 1.0 --proximity-duration 2.0
```
*Controls:* Press `q` or `ESC` in the playback window to exit.

### C. Run Member 1 Tracking Baseline (`main.py`)
```bash
python main.py --video data/v2.mp4
```

## 5. Member 2 Safety Analytics Details

### Event 1: Predefined Distress Gesture (`potential_distress_gesture`)
- **Definition**: Both hands/wrists intentionally raised above the shoulders/head region and held for a sustained period ($\ge 1.0\,\text{s}$).
- **Landmarks**: Left/Right Wrist and Left/Right Shoulder via MediaPipe Pose.
- **Rules**:
  - Wrist elevation: $y_{\text{wrist}} < y_{\text{shoulder}}$ for both wrists.
  - Landmark visibility: $\ge 0.5$ for all key landmarks.
  - Single raised hand is rejected.
  - Brief noisy raised hands are rejected via temporal frame counter ($\ge 10$ frames).
  - Maintained per `track_id` with a $5.0\,\text{s}$ cooldown to prevent duplicate alerts.

### Event 2: Sustained Proximity / Close-Following (`sustained_proximity`)
- **Definition**: Two tracked people remain unusually close while moving in correlated directions for a sustained period ($\ge 2.0\,\text{s}$).
- **Rules**:
  - Representative ground position: bottom-center of bounding box ($x = \frac{x_1 + x_2}{2}, y = y_2$).
  - Normalized distance: Euclidean distance scaled by average bounding-box height ($\le 1.3$).
  - Movement consistency: Cosine similarity of motion vectors ($\ge 0.40$).
  - Opposing path-crossings (e.g. walking past each other) are rejected.
  - Stationary standing bystanders (no active displacement) are rejected.
  - Maintained per canonical pair $(\min(id_a, id_b), \max(id_a, id_b))$ with an $8.0\,\text{s}$ cooldown.

## 6. Standard Safety Event Contract (Member 3 Handoff)

Member 3 only needs to consume:
```python
from src.detection.person_detector import PersonDetector
from src.safety import SafetyEventDetector

person_detector = PersonDetector(confidence=0.4, track=True)
safety_detector = SafetyEventDetector(camera_id="CAM_01")

for frame_data in person_detector.process_video(video_path):
    events = safety_detector.process_frame(frame_data)
    annotated_frame = safety_detector.annotate_events(
        frame=frame_data["annotated_frame"],
        events=events,
        people=frame_data["people"]
    )
```

Every emitted event conforms strictly to:
```json
{
  "event_type": "potential_distress_gesture",
  "track_ids": [2],
  "timestamp": 12.7,
  "frame_id": 381,
  "camera_id": "CAM_01",
  "confidence": 0.84,
  "status": "pending",
  "details": {
    "held_duration_sec": 1.4,
    "consecutive_frames": 14,
    "wrist_elevation": 0.22,
    "disclaimer": "Potential distress gesture requiring human verification."
  }
}
```

## 7. Event Types and Human Verification

The dashboard consumes only the existing Member 2 events:

- `potential_distress_gesture` — shown as **Potential Distress Gesture**.
- `sustained_proximity` — shown as **Sustained Proximity**.

Both are potential patterns, not confirmed incidents. A pending event means no human decision has been made. **Verify** means an operator reviewed and marked it for attention in this prototype; it is not legal proof of a crime. **Dismiss** records the operator's decision that the alert is false or non-actionable. Dismissed events remain in history.

The displayed Event Score is a heuristic score, not a calibrated probability. Tracking IDs are temporary video-scoped labels and do not identify people.

## 8. Database

SQLite persistence uses the Python standard library and stores event history in `data/events.db` (ignored by Git). The `events` table includes:

```text
id, event_type, track_ids (JSON), video_timestamp, frame_id, camera_id,
confidence, status, identity_key, source_video, created_at, updated_at
```

`identity_key` is unique so Streamlit reruns cannot insert the same generated event twice. All SQL values use bound parameters.

## 10. Privacy, Ethics & Limitations

1. **Generic Person Detection Only**:
   - The model is restricted to generic person detection (COCO class 0).
   - **No facial recognition**, gender classification, age estimation, or demographic profiling is implemented.
2. **Temporary Session-Level IDs**:
   - Tracking IDs (`Person 1`, `Person 2`) are short-lived video sequence counters. They do not represent real-world identities.
3. **Probabilistic Triage & Human Verification**:
   - System outputs are framed as **"Potential Safety Events"** or **"Potential Distress Gestures"**.
   - This is a prototype, not a crime detector. Human verification is required; "verified" records an operator review and does not establish a crime.
4. **Camera Distance Limitations**:
   - Monocular CCTV cameras cannot measure true 3D distances in meters; proximity is measured in normalized image-space scale.
5. **Heuristic Limitations**:
   - The predefined gesture and proximity heuristics can produce false positives and false negatives. Proximity does not prove stalking or harassment.
   - Perspective, occlusion, lighting, and image quality affect person tracking and pose visibility. Track IDs can change after occlusion.
   - Event scores are heuristic, not calibrated probabilities.
